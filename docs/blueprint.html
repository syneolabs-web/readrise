Prodoxity Blueprint · v1

Reading is the input.
Change is the output.

A private reading circle for close friends. Not a classroom, not a public book club — two to twelve people who know each other, reading something meant to change how they live, and actually checking whether it did.

§1 Thesis

Why not just use Perusall? Because it's built to make forty strangers demonstrate they did the reading — not to make three friends change a habit.

Every existing platform stops at discussion

Discussion is the middle of the funnel, not the end. Prodoxity's premise is that reading is an input and changed behavior is the output — and every feature either feeds that loop or gets cut.

Read→ Highlight→ Discuss→ Commit→ Check in→ Vault

Perusall and Hypothesis implement the first three. The last three, in amber, are the product — the entire reason it exists.

“Close friends” is a technical constraint, not a vibe

Small-group intimacy buys real simplifications. It's why Prodoxity can ship features Perusall can't justify — the assumption removes roughly 70% of what makes social reading platforms expensive.

  • Invite-code only, no discovery. No search, recommendations, public profiles, moderation queue, or abuse reporting.
  • Circles of 2–12. Every member loads in one query. No pagination, no fan-out service, no follower graph.
  • Trust is assumed inside the circle. No per-annotation ACLs — the circle is the permission boundary, so one join check gates everything.
  • Real-time is cheap. A dozen concurrent connections per circle, not a million. An in-process event bus is genuinely correct here.
§2 Anchoring

The tell: this bug looks perfect to whoever created the highlight. You only see it on someone else's screen — so you ship it.

The hard problem: where does a highlight actually live?

This is the part that “gets mathematically tricky,” and it's where the obvious implementation quietly breaks.

✕ The trap
{
  page: 3,
  x: 412, y: 887,
  width: 230, height: 18
}

Viewport pixels, at one zoom, on one window size, at one DPI.

✓ The fix
{
  page: 3,
  rects: [{ x: 0.121, y: 0.443,
            w: 0.377, h: 0.019 }],
  textContent: "…", textStart: 1840
}

Fractions of the page's own coordinate space. Never the screen.

Store raw getBoundingClientRect() output and the failures are neither hypothetical nor subtle: your friend reads at 150% and the highlight lands on the wrong line; they're on a 13" laptop instead of your 27" monitor and it's the wrong paragraph; they resize the window and every mark on screen shifts.

Normalize against the PDF page's intrinsic size instead, and rendering becomes a pure multiply against whatever size the page happens to be right now. Zoom, resize, DPI and device differences all become free — because the stored value never referenced the screen in the first place.

Why store the text too

textContent and character offsets ride along as a fallback anchor: if geometry ever fails to resolve, the highlight is re-found by locating its text in the page's text layer. Geometry is fast but brittle; text is slow but durable. Perusall and Hypothesis both layer their anchors for the same reason — storing both costs a few bytes and buys durability.

§3 Architecture

Rule of thumb applied throughout: pick the boring option, then write down the condition under which it stops being correct.

Decisions, and what each one buys

ChoiceInstead ofBecause
SSEWebSockets Traffic is ~99% server→client. The client already has HTTP POST for the other direction. SSE auto-reconnects and needs no upgrade negotiation.
In-process busRedis / Kafka ~12 clients per circle. A Map is the right structure at this scale; pretending otherwise is architecture cosplay.
JWT cookieNextAuth Six people who know each other. NextAuth solves OAuth federation — a problem this product doesn't have.
pdf.js directlyreact-pdf We need the text layer and intrinsic viewport dimensions. A wrapper abstracts away exactly the two things the core feature depends on.
Server ComponentsA REST layer Reads go straight to Prisma. API routes exist only for mutations and the stream.
SQLite → PostgresDocker Postgres Neither exists on the target machine. Schema is parity-safe (no enums, no scalar lists), so the switch is genuinely one line.
Stated limitation, not an oversight. The in-process bus is correct for one Node instance — local dev, a VPS, a single container. On Vercel or any multi-instance serverless deploy, live updates will not cross instances. Reads still work; only push breaks. The fix is one file: back lib/events.ts with Postgres LISTEN/NOTIFY or Redis pub/sub. Nothing else changes.

The single authorization gate

Every mutation and every document read passes through one question: does a Membership row link this user to this circle? Because circles are small and trusted, that's the whole model. Non-membership returns 404, not 403 — a private circle shouldn't confirm its own existence to a stranger.

Uploads live outside public/ and stream through an authenticated route. A PDF in a private circle must never be a guessable URL.

§4 Evidence

Driven, not asserted. Every claim below was produced by operating the real app, not by reading the code.

What was actually verified

  • Anchoring holds across zoom. The same highlight tracks its text exactly at 115%, 130% and 175%. Pinned by 12 tests so a regression fails CI rather than shipping.
  • Round-trip via real selection. A highlight made by actual browser text selection stored 13 normalized rects, every value inside 0–1. The API rejects anything outside that range — so a 200 is the proof no pixel leaked into the database.
  • Two independent derivations agree. A browser-created rect landed at x=0.11758; the seed, computing from Helvetica metrics, landed at x=0.11765. Both are the left margin (72/612 = 0.117647).
  • Spoiler gating works. A member on page 4 sees Chapter 3 locked: “unlocks when you finish page 6.”
